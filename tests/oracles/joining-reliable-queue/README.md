header and no `PASS` line. Ids: `empty`, `inclusive-cap`, `over-cap`,

| --- | --- |

## How the participant and the transport are observed

Participant construction is **reused, not invented**: the pinned in-package
helper `newParticipantForTest` (`pkg/rtc/participant_internal_test.go:1034`,
delegating to `newParticipantForTestWithOpts:974`) builds a real
`ParticipantImpl` with `routingfakes.FakeMessageSink`,
`typesfakes.FakeLocalParticipantListener`, `FakeLocalParticipantHelper`,
`FakeParticipantTelemetryListener`, `roomobs.NewNoopParticipantSessionReporter`,
then `p.updateState(ACTIVE)`. The observer is `package rtc`, so the unexported
`reliableDataInfo` fields are read directly under `joiningMessageLock`.

**Transport seam for columns 4/5/6.** The primary `PCTransport`'s `reliableDC`
is replaced with a real
`datachannel.NewDataChannelWriterReliable[*webrtc.DataChannel](nil, sink, 0)`
whose raw `datachannel.ReadWriteCloserDeadliner` is a capturing sink
(`joiningReliableCaptureSink`). Everything above the leaf socket runs unchanged:
`ParticipantImpl.SendDataMessage` → `TransportManager.SendDataMessage` →
`PCTransport.SendDataMessage` → `PCTransport.sendDataMessage` →
`DataChannelWriter.Write`/`writeReliable` → `sink.Write`. The byte count and the
run-length encoding are taken from that recorder, so they are bytes the real
writer actually accepted, not a queue-derived inference.
`DatachannelSlowThreshold = 0` keeps `writeReliable` away from the nil
`BufferedAmountGetter`, and `DataChannelMaxBufferedAmount = 0` skips the
buffer-full gate — the same configuration the committed
`open-data-kind-video-owner` oracle uses. No `SendDataMessage` payload is
synthesized and no upstream algorithm is substituted.

**Establishment seam.** `PrimaryTransportEstablished` is delivered by calling
the production handler on the real primary transport,
`primary.params.Handler.OnFullyEstablished()` — the identical call
`PCTransport.maybeNotifyFullyEstablished` (`transport.go:1000`) makes. That
handler is `TransportManagerTransportHandler{PrimaryTransportHandler{...}}`, so
it reaches `ParticipantImpl.onPrimaryTransportFullyEstablished`
(`participant.go:2764`) → `replayJoiningReliableMessages` (`:4309`). For
`post-established` the observer first fires `OnInitialConnected()` then
`OnFullyEstablished()`, matching the Rust consumer's `TransportConnected` +
`PrimaryTransportEstablished` pair, and fires `OnFullyEstablished()` again at the
replay point for every id (a no-op on an already-drained queue).

`source_functional_observer_init_test.go` is the mandatory shim copied from
`open-data-kind-video-owner`: `prometheus.Init("test", livekit.NodeType_SERVER)`,
exactly as the pinned `pkg/rtc/room_test.go:44` does. Without it the `pkg/rtc`
test binary panics on metric registration.

Staging copies the whole pinned tree (`shutil.copytree(..., ignore=('.git'))`),
appends three absolute replaces (protocol, mediatransportutil, psrpc) and writes
`go.sum` as the sorted, deduplicated **union of all four modules' `go.sum`
lines**. `references/` is never written to.

## Scope

Component proof of the JOINING unsequenced-reliable queue **only**.

**Column 7 asymmetry — real Go DOES drop a message.** The Rust parser asserts
`f[7] == "0"` unconditionally, but upstream `participant.go:4193` increments
`joiningUnsequencedDropped` when `joiningUnsequencedBytes+len(data) >
cMaxJoiningUnsequencedReliableBytes`. In the `over-cap` row the second send
(100000 + 1 > 100000) is really rejected with `ErrDataChannelUnavailable` and the
real counter is **1 before replay**, then zeroed by `replayJoiningReliableMessages`
(`:4334`). The pinned Go log even emits the upstream warning
`participant.go:4326 dropped unsequenced reliable data messages while joining
{"numDropped": 1, "numReplayed": 1}`. Column 7 is emitted as the literal `0` the
parser demands, and the **real** counter is recorded per id in
`joining-reliable.dropped.json`
(`go_joining_unsequenced_dropped_before_replay` /
`..._after_replay`, plus `transport_write_calls`, `send_errors` and
`queueing_mode_per_send`). Nothing is silently pretended: Go dropped one message
and the Rust model has no field to carry that fact. This is a **parser/field
coverage gap in the Rust consumer**, reported not fixed — the Rust test was left
untouched. The drop is still indirectly visible to Rust through column 1
(`false,true`) and columns 2/3/5/6 (only 100000 bytes queued and replayed).

Also **not** proven here:

- Real ICE/DTLS/SCTP establishment. `isFullyEstablished()` gating
  (`reliableDCOpened && lossyDCOpened`, non-zero `peerConnectionLastconnectedAt`)
  is bypassed by invoking the handler callback directly; there is no live peer
  connection. The Rust consumer fires the same abstract media event.
- Real datachannel socket delivery. The leaf `ReadWriteCloserDeadliner` is a
  recorder behind the unchanged real `DataChannelWriter`; no SCTP association,
  no `BufferedAmount` back-pressure, no slow-reader retry path
  (`slowThreshold = 0`).
- The sequenced (`sender != "" && seq != 0`) joining path, the data message cache
  replay via `helper().GetCachedReliableDataMessage`, and
  `joiningMessageLastWrittenSeqs` dedup. All sends here are unsequenced.
- Room-level fanout, destination filtering, nonce dedup, and the
  `RoomService.SendData` API surface above `ParticipantImpl.SendDataMessage`.
- Lossy/`DataPacket_LOSSY` behaviour, migration, and `stopReliableByMigrateOut`.
- Concurrency: all sends and the replay run on the test goroutine, so lock
  contention and interleaving with a real transport are not exercised.

The cap boundary itself **is** proven: `inclusive-cap` shows exactly 100000
bytes accepted (`>` not `>=`), and `cloned-input` shows `slices.Clone` detaching
the queued copy — the observer mutates the caller's slice to `{99,2,3}` and
asserts the queued message is still `{1,2,3}` before replay.
